# HTM 恢复至 1.4.0、QTM 独立实现方案

日期：2026-09-30。审查版本：`c01d90d`（v1.7.1）。本文件是实施任务书，本次未执行回退、重编译或生产代码修改。

验收规模已按用户要求缩减：默认只用 **2 个固定诊断状态 + 2 组实拍状态**，另保留少量快速正确性/生命周期检查。原大集合仅作故障调查备用，不再是必跑项；第 5–6 节和文末实施指令为准。

## 1. 决策

采用两阶段交付：**先恢复基于 1.4.0 的完整 HTM 应用并验证真实包性能，再在该稳定底座上接入独立 QTM 引擎。** HTM 恢复是第一项可独立验收的成果，不等待 QTM 新一轮算法优化。

隔离做到源码、构建、二进制、进程、资产、缓存和验收七个层面。请求只在服务入口按 metric 路由一次；HTM 搜索内部不再承担 QTM 的分支、状态字段、候选调度和资产初始化。

1.4.0 的准确来源是提交 `ae73ca81af1ed077c059f3345377190bf0ce2882`，其中 `cube_app/__init__.py` 的版本为 `1.4.0`。当前本地没有 `v1.4.0` 标签，实施时使用该提交，不猜测标签。现有 1.7.1 及其 QTM 资产作为可追踪的独立迁移来源保留。

新发布版本应递增，写明“HTM 内核恢复到 1.4.0 来源”，不重用旧版本号或覆盖旧标签。回退恢复的是代码行为和性能基线；既有 1.4.0 数据没有证明所有真实状态都能在 180 秒内完成严格最短证明。

| 事实 | 代码或报告依据 | 对方案的影响 |

`initial/` 实际包含 1–16 共 16 组、96 张六面图片。现有 `test_real_images.py`、`extract_real_patches.py` 和 `real_color.test.js` 只覆盖 1–7 组，**8–16 组未进入现有真实图片回归**。已有三阶参考标注为 1、2、5 组；3、4、6、7 组为二阶。本轮检查了 8、12、16 组 U 面，均为三阶；其余新增组的阶数和各组全部面片仍需核对。图片 hash、覆盖情况和已通过合法性校验的三组三阶参考串见[实拍样本清单](benchmarks/htm-qtm-initial-inventory-2026-09-30.json)。

## 3. 目标结构与边界

以下为待实现结构，不是当前已有路径或命令：

```text
server.py / web
    └── cube_app/solvers/router.py       # 请求边界路由；任务 ID、deadline、资源额度
          ├── htm/backend.py            # HTM 适配器，兼容 1.4.0 原生协议 v2
          │     └── cube_solver_htm.exe # 仅 HTM
          └── qtm/backend.py            # QTM 独立协议、候选与证明
                └── cube_solver_qtm.exe # 仅 QTM

native/htm/{include,src,build.ps1,build_tables.ps1,build_profiled.ps1}
native/qtm/{include,src,build.ps1,build_tables.ps1,build_profiled.ps1}
cube_app/solvers/{contracts.py,router.py,resource_broker.py}
cube_app/solvers/htm/{backend.py,native.py,optimal.py,fast.py}
cube_app/solvers/qtm/{backend.py,native.py,optimal.py,fast.py,small_tables.py}
assets/htm/<asset-version>/manifest.json + PDB
assets/qtm/<asset-version>/manifest.json + PDB
.cache/htm/<coordinate-version>/
.cache/qtm/<coordinate-version>/
tests/htm/    tests/qtm/    tests/solver_contract/
```

### 3.1 允许共用的内容

- 拍照识别、颜色校验、页面、用户输入和最终动作显示。
- 请求级面片串和动作字符串规范、合法性检查、最终动作重放验证。
- 不含搜索策略的事件类型、统一任务 ID、绝对 deadline 与资源额度分配。
- 两种 metric 的显示与代价校验函数；这些函数只在边界使用。

### 3.2 必须独立的内容

- DFS/IDA*、搜索状态布局、动作扩展、剪枝顺序、方向选择、线程池、TT、Tail、候选算法。
- 坐标表、小剪枝表、PDB 读取器/建表器、默认参数、PGO 训练与产物。
- 原生进程、启动握手、初始化、取消与重启、证明缓存、Python 回退实现。

迁移第一阶段允许复制底层 C++ 魔方运算代码到两个引擎，保存来源 hash。先恢复性能，再考虑提取真正稳定的纯函数库；不能为了消除重复代码重新建立共享热路径。HTM 构建不得编译、链接或包含 QTM 源码。QTM 可以保留其自身需要的 HTM 代价辅助表作合法下界，但该表必须列在 QTM 自己的清单内，不能依赖 HTM 服务或读取其私有缓存。

### 3.3 请求与结果契约

外层 API 保持 `metric=HTM|QTM`，默认 HTM。HTM 适配器转换请求为 v2 协议并验证返回，不强迫旧 EXE 满足“同时支持 HTM 和 QTM”的握手。若需要扩展诊断字段，优先在适配器补充；不可为兼容而信任错误 metric 或跳过动作重放。

统一结果包含：`metric`、`moves`、`cost`、`optimal`、`status`、`lower_bound`、`upper_bound`、`completed_cost`、`engine_id`、`engine_version`、`asset_profile`。无法获得的旧协议字段留空，不编造。

“找到可执行解”和“证明它最短”分开显示和统计。HTM 候选按 QTM 重新计价后只能成为 QTM 上界，不能继承 HTM 的 `optimal=true`。缓存键至少包括引擎、metric、证明规则版本、规范状态与成本范围，资产/坐标快照有独立身份；两种 metric 的证明永不互用。取消、超时或预算耗尽不会产生新的最短证书。

### R2：HTM 独立封装，保持恢复版行为

1. 在 R1 已验证的结果上迁移到 `native/htm` 和 HTM Python 适配器，生成独立的 `cube_solver_htm.exe`。核心文件保留 H0 字节或登记必要差异，构建源列表使用显式白名单。
2. 给 HTM 单独的 EXE 路径、工作目录、环境和缓存根。通过旧 EXE 已支持的 `CUBE_NATIVE_COORDINATE_CACHE` 指定 HTM 坐标缓存；PDB 通过自己的绝对路径传入。
3. HTM 请求不得初始化 QTM Python 表、导入会执行 QTM 重型初始化的模块、启动 QTM 进程或扫描 QTM 资产。薄路由采用惰性导入。
4. HTM 的 native/Python/quick 路径一起隔离；不能只拆原生 EXE，却继续调用被 QTM 改造后的 Python 求解器。
5. 二阶 HTM 保持 H0；以后接回二阶 QTM 时也用独立距离表和延迟初始化，不与三阶核心共用 metric 分支。

**通过条件：** H0 与 H1（封装后的 HTM）在确定性完整排除层的节点/剪枝结果一致；热搜索和实际包启动达到第 6 节门槛。

### R3：将现有 QTM 提取为独立实验引擎

1. 从冻结 Q0 迁移 QTM，而不是从已恢复 HTM 中再次加 `if (metric == QTM)`。初版先忠实保留 Q0 算法，再逐项去除 HTM 运行接口；其正确性先与 Q0 做对照。
2. 保留已有实证成果：加权 QTM 基础 PDB、强联合 PDB、仿射坐标、精确 nibble 读取器、QTM 三轴加强、奇偶预算、原生候选。强表不因目录变更重新建表。
3. dual/BPMX/预取继续作为 QTM 内部实验开关；方向策略保留 off/legacy/bounded 对照，不能因上一轮总体更快就认定每个真实状态都适用。
4. QTM 配置和状态结构只服务 QTM；C++ 和 Python 回退、候选器、建表、PGO、日志均在 QTM 自身目录。QTM 启动能力判断不再依赖 HTM Corner/Phase-1 文件是否存在。
5. `QTM base/standard/strong` 明确区分。正式性能版要求完整 QTM Corner/Phase-1、已验证强表，以及与验收一致的 Tail 配置；缺表时报告真实配置和回退原因，不能以 `strong` 名义运行。
6. 首版将 QTM 作为可选实验组件：未安装时 UI 不提供可执行入口，API 返回明确的不可用状态；安装并启用后才按需启动。HTM 恢复不依赖它是否达标。

**通过条件：** Q0 与独立 Q1 在相同资产、参数下通过第 5 节精简对照；QTM 目录或 EXE 缺失时，HTM 快速正确性与路由检查仍通过，不重复长性能测试。

### R4：进程、内存和调度隔离

独立进程仍可能争用 CPU、内存和文件缓存，因此需要资源策略：

- 两个后端各自有进程、锁、队列和取消通道；外层资源分配器只管理额度，不实现搜索策略。
- 单机默认同一时间运行一个高负载证明。HTM 默认优先；用户切回 HTM 时，在有界检查点取消或让出 QTM 当前未完成层，必要时退出 QTM 进程释放大表。完整已证明事实按版本校验后才能复用，未完成前沿不冒充可恢复证明。
- QTM 不随应用启动预热；后台资产校验也占资源额度。HTM 请求开始时不能继续进行 QTM 强表全量校验或建表。
- 分别限制两个引擎线程数和内存。安装了 QTM 但未使用时，HTM 的工作集和线程数应与 HTM-only 一致。并发模式仅作为显式选项，单独测量且总线程数受控。
- QTM 崩溃、协议错误、加载失败和取消不重启 HTM 进程。HTM 请求不因 QTM 锁被占用而等待完整 QTM 搜索结束。
- 资源让出目标为 1 秒内；超过 2 秒记录故障并在进程级终止对应 QTM 任务，动作、完成证书与未完成层的处理分别记录。该数值是待验证的产品目标。

**通过条件：** QTM 未安装、已安装未启动、启动失败、完成后闲置、运行后切回 HTM 五种情况均验证。QTM 活跃时的 HTM 体验必须计入让出时间，不能只测两个引擎单独运行。

### R5：以真实端到端问题决定 QTM 下一轮算法工作

先建立每个请求的时间账本：排队、引擎启动、基础 ready、强表 ready、首候选、证明 CPU/墙钟、最终返回。同时记录实际 EXE/资产、回退原因、线程数、每层生成量与完成成本。

按测到的原因决定下一步，避免再次只用局部微基准推动大改：

| 观察 | 必做动作 | 判定依据 |
| --- | --- | --- |
| 实包没有 QTM 强资产，或进入 Python/弱表回退 | 先修安装清单、能力检查和可见状态，重测同状态 | 发布包与实验包的 asset/profile/hash 对齐 |
| 大部分期限耗在初始化、排队或 strong 尚未就绪 | 处理加载/资源调度，分别测 eager 与 staged | deadline 从用户提交开始；低强度长层的等待不能隐藏 |
| 相同预算生成量明显高于强配置基线 | 检查正确的表、三轴规则、方向和候选上界是否实际生效 | 相同输入和参数逐层对照 |
| 搜索量相近而单节点处理明显变慢 | 比较编译配置、QTM 独立状态布局和内存访问 | 固定完整层、同线程，区分单位成本与算法树大小 |
| 强配置已就绪但 20/21 成本证明仍主导 | 在 QTM 分支专项研究更强下界、方向组合或不同搜索方案 | 先给可采纳性证明、资源成本和真实困难集试验；不改 HTM 核心 |

不删除当前 QTM 的有效优化后从零重写所有建表器，也不把“拆成两个 EXE”本身算作 QTM 搜索提速。完成隔离后，用真实样本结果另行决定有成本的算法投入。

### R6：构建与发布同步隔离

1. 两个构建目标生成不同路径、EXE 名称、build-info 和 PGO 文件；构建 QTM 不覆盖 HTM，CI 不依赖上次缓存偶然存在的资产。
2. 默认稳定包只含 HTM 及完整 HTM 运行资产；QTM 采用独立可选组件或明确命名的含 QTM 包。QTM 的 base/strong 配置写进发布文件名与 manifest。
3. CI 最小测试配置与正式发布资产配置分离。HTM 正式包显式要求 Tail-6；QTM strong 包显式要求强表及匹配 Tail。不能继续以默认 `QtmProfile=None` 构建后沿用 strong 性能结论。
4. 资产预检核验 metric、版本、完整标记、大小、checksum/hash、坐标版本和来源；文件存在或超过 1 MB 不等于正确配置。
5. 解压最终待发布 ZIP 到独立 Unicode 路径，在无法访问仓库 `.cache` 的环境实跑。报告实际打开的资产路径，防止验证脚本偷偷从源码目录补表。
6. 单独建立 HTM 和 QTM 正确性任务、HTM 性能门槛以及装包/资源隔离测试。QTM 改动触发 HTM 保护性验收，HTM 不达标不能因 QTM 总体快而放行。

**交付：** HTM 恢复包、可选 QTM 组件、每包清单、构建来源与解压后实跑报告。远程发布不属于仅制定本方案的当前请求。

## 5. 数据集和测量方式

### 5.1 固定的小集合

| 用途 | 输入 | 默认执行方式 |
| --- | --- | --- |
| 快速正确性 | 从已有回归中固定 8 个有准确答案的浅层状态，覆盖复原态、单转、半转和混合动作 | 每个一次，核对代价、动作重放和最短标记；HTM/QTM 分别计价 |
| 开发性能 | `tests/native_cases.json` 中的 `pgo16`、`known18`，共 2 个 | 比较固定可完整排除的成本层，每个 3 次，单次最多 5 秒 |
| 最终真实验收 | `initial-1`、`initial-12`，共 2 个三阶状态 | 每个、每引擎、每版本只跑 1 次，最多 180 秒 |
| 快速集成 | 取消后再求解、QTM 缺失、QTM 故障、QTM→HTM 资源让出、二阶 HTM 各一项 | 复用简单状态，使用短期限，不为每种组合启动深层证明 |

选择第 1 组是因为已有参考标注，第 12 组用于覆盖新增实拍；**在看到新版成绩前固定选择**。若第 12 组存在无法消除的标注歧义，先记录原因，再按固定次序改用第 8 组；不得因为搜索慢而替换样本。`pgo16` 属于已有训练样本，因此保留 `known18` 与两组实拍作为补充，不将它单独用于宣称总体提速。

开发诊断先在各自基线上选择能在约 1–3 秒内完整排除的成本上限，单个状态校准最多 10 秒，然后对新旧版本冻结同一上限。HTM 与 QTM 可用不同成本上限；超时不能充当完整层证书，发生超时就缩小预算后同时重测对应的新旧版本。

**不再默认运行：** HTM 原 8 状态全集、QTM 48+32 状态、额外随机保留集、全部 16 组照片、多线程扩展矩阵、每个真实样本三次重复，以及所有实验开关的笛卡尔组合。现有原始数据留作参考，不自动重跑。

### 5.2 时间预算与复用

- 开发性能每个引擎最多 `2 状态 × 2 版本 × 3 次 × 5 秒 = 60 秒` 搜索时间；两个引擎全部改动时最多 2 分钟。只有受影响的引擎需要重测。构建、资产校验和首次启动另计并记录。
- 最终 HTM 对照为 `2 实拍 × 2 版本 × 180 秒`，最坏 **12 分钟**；QTM 独立迁移再按同样方式验收，最坏 **12 分钟**。两者合计最多 **24 分钟请求预算**，顺利完成时提前结束。180 秒包含请求排队、启动和搜索。
- 最终长测试直接在待交付解压包上执行，不在源码版再重复同一轮长测试。源码用短诊断验证；只有源码/实包行为不一致时才补测对应状态。
- 新旧基线参数、EXE/资产 hash 和运行环境不变时复用已测结果，不为每次适配器修改重跑 H0/Q0。候选版本发生影响性能的变化时，只更新受影响项；环境或机器负载明显变化则重新配对。
- 只选一组本机实际生产线程数作为主验收配置，所有版本一致。只有并发/线程相关故障才增加单线程诊断。

### 5.3 正确性、识别与异常复测

两组实拍先一次性核对图片→参考 facelets，保存图片 hash、方向和标注；自动得到合法状态不等于识别正确。最终包从图片路径进入 HTTP 求解，记录提交的 facelets，确保新旧版本求解同一状态。固定 facelets 的重复长测试仅用于定位识别与搜索差异，不作为额外常规任务。

纯证明短诊断关闭候选和证明缓存，使用相同初始上界；真实长测试启用正常候选，记录首候选时间、最终代价、完成成本和终态。两项长测试逐状态报告，不再计算小样本 p95，也不设置“总体成功率 ≥80%”这种与两状态规模不匹配的门槛。

仅在出现代价错误、非法公式、误报最短、确定性搜索量不一致、HTM 基线完成而新版超时、或短诊断耗时回退超过 10% 时复测对应项。计时异常先补测该短用例；180 秒临界状态最多补一轮对应的新旧配对，不立即扩大到整个集合。修复后复测失败项及其直接相关检查。

若修改了坐标映射或剪枝合法性，针对该规则补独立 oracle/等价验证；纯目录、协议和打包迁移不默认重跑所有浅层枚举。确需增加状态时一次只增加最多 2 个与故障有关的诊断样本，先采用 30 秒上限，报告新增原因；不自动恢复大规模验收。

## 6. 验收门槛

| 门槛 | 验证方式 |
| --- | --- |
| HTM 正确性与 H0 一致 | 8 个浅层准确答案、公式重放及快速生命周期检查通过；选定完整排除层的确定性节点/剪枝结果一致 |
| HTM 恢复性能 | 同编译模式/资产/线程，两个短诊断逐项中位耗时回退不超过 10%；超过时定点复测，确认持续退化则阻断 |
| 真实个案不被平均掩盖 | 两组实拍逐项比较；H0 完成而 H1 超时必须调查，双方都超时则比较已完成成本并明确基线限制；临界情况按第 5 节补一轮 |
| HTM 接入层开销 | 用短状态测候选交付与启动，不计算小样本 p95；明显新增等待、错误回退或加载 QTM 资产均阻断 |
| QTM 对 HTM 零依赖影响 | QTM 缺失不影响 HTM；未启用时 QTM 进程数为 0、无 QTM 资产映射；HTM 启动与工作集相对 HTM-only 在测量误差内 |
| 资源让出与故障隔离 | QTM 运行后切回 HTM 的额外延迟目标 ≤1 秒；QTM 故障不能破坏 HTM 当前任务或候选 |
| QTM 迁移不退化 | 两个短诊断同配置完整层与结果一致；逐项中位耗时回退超过 10% 时定点复测；不要求动作串完全相同 |
| QTM 用户体验 | 两组实拍分别报告首候选、代价、180 秒证明终态及与 Q0 的差异；未证明则保持明确的实验状态，不用两例宣称总体性能达标 |
| 最终包与报告一致 | EXE/资产 hash、参数、实际路由一致；解压包直接通过正确性、困难 HTM 样本和真实请求验收 |

这些阈值是精简验收的实施目标，不是当前已测到的结果。小集合用于确认恢复和隔离效果，不足以证明任意真实状态的成功率。QTM 仍有真实样本未证明时保持实验说明，不阻塞已通过的 HTM 恢复包。HTM 在 H0 上本来就超时的样本如恢复后仍超时，应标为基线能力限制，与本轮回归区分。

## 7. 执行顺序与提交边界

```text
R0 冻结现场 → R1 完整 HTM 恢复与可运行包 → R2 HTM 独立封装
                                            ↓
                         R3 QTM 独立迁移 → R4 资源隔离
                                            ↓
                           R5 真实样本诊断 → R6 双构建与最终装包验收
```

建议按“恢复应用、隔离 HTM、迁移 QTM、接入路由与调度、修正发布、真实验收”独立提交。不要先把当前共享求解器拆成两个相同副本，就宣布 HTM 已恢复到 1.4.0；HTM 来源必须是 H0，并由测试证明。

产物包括：源代码与构建脚本、基线/包资产清单、真实样本文件、每状态原始测量、完整报告 `docs/htm-rollback-qtm-isolation-report.md`。报告必须回答：实际退化由哪些已验证因素造成，HTM 是否恢复，用户真实状态是否改善，以及 QTM 还有哪些未完成指标。
