H1 的具体依据是 [HTM 候选器](../cube_app/solvers/htm/fast.py) 会先找到解，再在最多 1.5 秒的候选预算中继续改进，最后返回。[server.py](../server.py) 已经先启动原生证明，两者可以重叠；这里要缩短的是“已找到候选但尚未发布”的时间，不是重新设计所谓串行证明流程。保留快速证明优先、最佳候选单调改进、合法动作重放和原绝对 deadline。请求已经取消、完成或被新任务替换时，旧回调不得更新结果。首候选响应发出后，后台改进仍受原资源配额和期限约束。

H1 首轮保持 Python 候选算法及现有预算，先隔离通知机制的收益。若计时随后证明候选搜索本身占主要成本，再安排 HTM 独立的原生两阶段候选器；使用 HTM 自己的表与计步规则，不能导入 QTM 引擎或表来获得速度。网页首次候选变快只能称为交付改善，严格最短确认时间也下降才计入完整求解提速。

H2 的明确入口是 [HTM depth_first_search](../native/htm/src/solver.cpp)：剩余深度至少 12 时创建 `std::vector<Candidate>`、`reserve(15)` 并调用 `std::stable_sort`。固定数组及稳定插入排序可以消除这条路径的动态分配；根最多 18 个动作，数组必须容纳 18 项，同下界时维持原动作顺序。该分支并非每个节点都执行，收益大小尚未测量。以完整排除树的生成量不变、墙钟下降作为证据，不预先承诺百分比，也不顺带启用全层置换表。

Q1 的入口是 [QTM CoordinateTables::evaluate / expand](../native/qtm/src/solver.cpp)。当前已有 strong-first、延迟坐标展开、仿射坐标及被完整大表覆盖的小表省略。下一步应针对默认“完整 QTM strong、strong-first、dual off、prefetch off、slice keep”配置提取专用路径，而不是再次实现这些机制。是否使用模板或独立函数由编译结果和采样决定；确保拒绝节点无需补齐多余坐标，接受节点则具有后续递归和 materialize 所需的全部字段。

Q1 保留 base、partial、缺表和损坏资产的通用回退。strong/Tail 更换只在已有安全边界重新选择路径，使用同一层持有的不可变快照，不能热替换正在访问的裸指针。完整层生成量与各类拒绝量应可对齐；若结果改变，先查语义差异，不以“更快”掩盖遗漏搜索。目标是降低每次展开成本，先争取暖搜索中位数下降 10%，不通过减弱校验、取消检查或证明条件换时间。

Q2 的 [原生候选器](../native/qtm/src/fast.cpp) 已有三轴正逆共六种变换、QTM 加权两阶段搜索、动作归并和 Tail 窗口替换；[调度代码](../native/qtm/src/solver.cpp) 的多线程候选预算最多 3 秒，单线程另有较短预算。因此下一步不是增加六方向，而是在同一总预算内记录各方向首次候选、改进成本和节点消耗，测试更合理的短片分配，避免一个方向先耗尽改进机会。不能根据 initial 的具体 Facelets 硬编码选方向。

Tail 局部改进作为 Q2 的另一个独立变体：当前候选工作线程绑定启动时的 Tail 快照，staged 启动时未必已有 Tail。若该情况确实出现，待 Tail 完整验证并采用后，对已有候选安排最多一次、例如上限 0.2 秒的局部改进；只占用一个获得许可的候选额度，引用持有的有效快照，期限沿用原请求。比较最终上界下降带来的收益与挤占证明线程的损失，不能仅凭候选短了就启用。此处 0.2 秒是待校准参数。

Portable PGO 要先补齐 QTM 构建支持：[现有 QTM PGO 脚本](../native/qtm/build_profiled.ps1) 使用 `-march=native`、`-mtune=native` 并标记 `portable=false`，不能直接充当通用发布构建。增加 Portable 参数及调用链透传，固定 x86-64 通用指令；两引擎分别记录训练集、源码、编译器、参数和 EXE 散列。训练使用独立固定打乱，覆盖正常候选和实际默认强表路径；六个 initial 验收状态全部排除。普通 O3/LTO 与 Portable PGO 分开对照，保留普通构建回退。

P2 暂不纳入首轮承诺。若 worker 统计显示明显尾部空闲，先测现有队列和切分粒度，再考虑任务分发改造；QTM 本来已有 adaptive split。若强表查询成本占主导，才测试低频选择性逆状态下界；根正逆下界和现有有界方向探测已存在，需要证明新增查询的成本小于节省的搜索。任何新剪枝必须先说明下界合法性，再过独立 oracle。更大的 PDB、Tail 和 GPU 路线另立资产、内存与可移植性评估，不与本轮软件热路径收益合并。

| 口径 | 配置和用途 | 需要输出 |
| --- | --- | --- |
| 完整排除层 | 资产 eager 就绪；关闭候选、证明缓存及方向变更；同一方向、线程数、成本界和资产。只选完整排除且未找到解的层 | 客户端墙钟、原生 elapsed、生成量/秒、查询及拒绝计数、worker busy/idle、完整成本界 |
| 默认首次完整请求 | 实际包普通启动、默认 staged、原生进程为新进程；不注入已知最优解，不复用已证结果；从零生成候选并验证 | 首候选产生/交付时间、候选上界曲线、初始化和采用时间、严格确认时间、终态及下界 |
| 进程复用与资源回归 | 原有 bounded reuse；用不同浅状态，另外关闭证明缓存检查同状态不走证书捷径 | warm startup、TTL、取消清理、1/2/3 线程进展、HTM 抢占等待、工作集峰值 |

完整排除层可复用 [benchmark_isolation_short.py](../tests/benchmark_isolation_short.py) 的 HTM 协议处理及 [benchmark_qtm_production_pair.py](../tests/benchmark_qtm_production_pair.py) 的交错方法，补成对两种度量都可配置的统一脚本。现有 QTM 完整层状态为 `pgo16 / bound 19`、`known18 / bound 18`；HTM 单独校准成本界，使一次约 0.2–2 秒、硬上限 5 秒。未知最短距离不能靠候选上界判断某一层一定无解；必须先由基线完整排除，再固定该界。

单因素每引擎采用两个完整层、每版本三次，顺序预先固定为 AB、BA、AB，最多 60 秒搜索预算。只在遇到事先定义的外部干扰时作一次有记录的复测，不反复跑到结果好看。热路径/PGO 变化应保持完整树生成量一致；后续剪枝变体允许生成量变化，但必须另外核对合法性和完整覆盖，不能再把它解释为同树吞吐对比。

开发阶段固定参考机可用线程配额；当前 16 逻辑 CPU 参考配置采用 15 个总额度。候选、loader 和证明共享额度，不能让变体多用线程。冻结 CPU、内存、编译参数、默认开关及资产 profile，计时期间不同时构建、跑另一个引擎或执行其他性能测试。新进程加暖 OS 文件缓存明确记为该条件，不称为冷磁盘性能。

最终默认请求按六状态 × 两度量 × 新旧两版本 × 三次进行，共 72 次，每请求最多 30 秒，名义求解预算上限 36 分钟；构建、页面准备和清理时间另计。这是后续完整验收规模，不在本次方案任务中运行。每状态按 AB、BA、AB 配对，各次重新建立受控服务，确认没有已有 job、incumbent 或 proof cache；状态顺序预先冻结，不并行跑两个引擎抢占资源。

使用实际包的正常页面请求与原有轮询，采集页面自身收到的候选及终态；后台事件另外记录原生计时，不增设高频轮询改善表面成绩。请求 deadline 从原入口继承，初始化、等待均计入，不能到 strong ready 后重置。UI 轮询造成的终态观察延迟单列。可复用 [真实页面验收脚本](../tests/verify_qtm_production_page.cjs)，但需先去除仅限两组 QTM 的假设并支持本轮矩阵，不能把它描述为现成覆盖两个引擎六组。

每条记录至少包括版本与 EXE SHA、状态与照片/Facelets SHA、metric、线程配额、加载/复用状态、首次候选成本及时间、每次上界改进、strong/Tail ready 与 adopted、完整排除层、搜索计数、候选与最终公式、请求终态、工作集峰值。通过独立 Python cubie 重放所有交付公式并重算成本：HTM 半转为 1，QTM 半转为 2。

最短性验收依赖完整排除和合法下界：HTM 需排除候选成本以下的所有可能层；QTM 保留合法的成本奇偶性跳层。`completed_depth` 可以包含数学排除的不可能成本，不能冒充额外搜索量。超时、取消、预算不足或被候选更新打断的层都不能签发完整层证明；动作可复原不等于已经证明最短。

建议在实施前冻结以下门槛：

| 项目 | 采用条件 |
| --- | --- |
| 正确性 | 独立重放、两种成本、已知最优案例全部正确；新增四组候选合法；完整/部分/缺失/损坏资产、取消与期限测试通过；需要完整资产的门禁不允许静默 skip |
| 单项热路径 / PGO | 完整层中位数有可重复的至少 5% 改善，非目标层无超过 5% 的可重复退化；未过则保留旧路径。Q1 争取 10% 改善 |
| H1 首候选交付 | 对实际出现发布等待的状态，争取中位数下降至少 20%；快速完成状态不退化。只改善候选交付时，结论明确限定于此 |
| 各引擎最终速度 | 分别争取全六状态 PAR-2 均值下降至少 15%；新旧均完成的配对另报每状态时间中位数和几何平均比值；既有可完成状态不能出现新的超时，单状态超过 5% 的可重复退化需解决后再采用 |
| QTM 既有收益 | 首候选、strong 采用延迟、总线程配额、TTL 与 HTM 优先准入均保持；不能用启动/复用回退抵消热搜索收益 |
| 资源 | 首轮保持表文件格式、规模与数量；同机工作集峰值不出现超过基线 5% 的未解释增长；1/2/3 线程路径有进展且可取消 |

PAR-2 以原请求 deadline 内后台确认严格最短为成功：成功取完整请求耗时，30 秒仍未确认取 60 秒惩罚；页面观察时间另报。每个状态三次全部保留，不能只平均成功请求。若新旧都超时，记录该状态的候选成本、已证下界及差值；这些可说明进展，不能伪装成已测得的严格完成加速。六个状态仍只是固定回归集，不据此宣称总体 p95、任意打乱成功率或普遍 30 秒保证。

实施后的交付物应为：独立的基线身份清单、补齐后的六组用例、可复现的单因素与正式请求脚本、全部原始事件及失败记录、逐项采用/拒绝结论，以及通过验收的实际包。沿用 HTM/QTM 各自目录、表与缓存的隔离，保留共享 broker 的 HTM 优先语义；历史“HTM 与 H0 字节一致”是旧迁移验收证据，本轮有意修改 HTM 时应记录相对新基线的差异，不能同步篡改历史冻结副本来通过旧检查。
