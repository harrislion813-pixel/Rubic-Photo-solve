# 相同打乱状态下 HTM / QTM 的理论计算耗时

日期：2026-10-01（Asia/Shanghai）。范围：三阶魔方，计算候选解与证明最短性的用时。这里的“理论”是指定搜索算法、剪枝配置和硬件吞吐后的模型，不是仅由计步规则决定的秒数。

**结论：QTM 与 HTM 没有固定耗时倍率。** 最短距离、完整排除的成本层、剪枝后的生成量、每次生成的成本，以及找到最优候选的时机共同决定时间。`26 / 20 = 1.3` 不能用作计算耗时比例。

## 1. 理论模型

对于固定状态和固定配置，已经加载资产的搜索时间可近似写成：

\[
T_{\mathrm{search}} \approx
\frac{N_{\mathrm{exclude}} + N_{\mathrm{discover}}}{V},
\]

其中 `N_exclude` 是排除更短解所生成的候选节点数，`N_discover` 是找到/改进可执行解的额外搜索量，`V` 是该配置的实际候选生成吞吐，单位为次/秒。完整请求还包括排队、初始化、加载等待和通信。候选生成与证明可能并行，不能机械地把两个计时相加；动态线程分配也会改变 `V`。

两种规则在本项目里都使用 18 种动作记号。HTM 的动作代价均为 1；QTM 的 12 种四分之一转代价为 1、6 种半转代价为 2。因此，QTM 的“成本深度”不等于动作记号个数。

只保留代码中的相邻同面合并、相对面交换规范化，忽略 PDB、Tail、状态去重等剪枝时，可以精确递推规范动作序列数量。六面转移矩阵的最大特征值为：

\[
\lambda=2+\sqrt6.
\]

HTM 每面有 3 种单位代价动作，QTM 每面的代价生成函数为 `2z + z²`。由此得到按成本计算的渐近扩张率：

\[
b_H=3\lambda=13.348469,\qquad
b_Q=\lambda+\sqrt{\lambda^2+\lambda}=9.373660.
\]

HTM 数值与 [Korf 的原始论文](https://www.cs.princeton.edu/courses/archive/fall06/cos402/papers/korfrubik.pdf)一致；QTM 数值由本项目加权动作和同样的面规范化规则推导。它们表示未使用领域剪枝的序列树增长率，不是不同魔方状态数，也不是实际引擎的固定耗时倍率。

例如，对完整遍历至给定成本界的一棵规范树，精确递推结果为：

| HTM 成本界 | QTM 成本界 | QTM / HTM 序列节点数 |
| --- | --- | ---: |
| 17 | 20 | 1.993 |
| 18 | 20 | 0.149 |
| 18 | 22 | 13.121 |

此表不计实际剪枝、不计迭代重访，也不计找到解时的提前停止；不能直接乘一个实测秒数来预测完整求解。它说明仅知道 QTM 步数较多，仍无法确定时间倍率。

QTM 解的成本奇偶性由角块排列奇偶性确定，本项目因此以 2 为间隔推进证明成本界。最优成本为偶数 `d` 时，排除到 `d-2` 的完整搜索配合奇偶性即可排除所有更短成本；`d-1` 不需要另搜。`completed_depth` 可以包含这种数学排除，不能误当作额外完成了一棵搜索树。HTM 没有相同的成本奇偶限制。

同一状态满足 `d_H ≤ d_Q ≤ 2d_H`。三阶的全局最大最短距离为 [HTM 20](https://www.cube20.org/) 和 [QTM 26](https://www.cube20.org/qtm/)；这是各自的最大距离，不能替代给定状态的距离或运行时间。

## 2. 当前引擎的同机证明校准

本次以 `tests/initial_solver_cases.json` 中两组固定 Facelets 为输入，并逐字匹配历史记录。每种度量的已知最优动作先经独立 Python cubie 模型重放、重算成本，再交给当前引擎。**这是“已有最优候选后，完整排除更短解”的时间，不是从头发现最优解的时间。**

配置：16 个逻辑 CPU，15 个搜索线程；每请求最多 30 秒；HTM 完整基础表 / Tail-6，QTM 完整 strong / Tail-8；正向；关闭方向探测和 QTM dual；关闭候选搜索和证明缓存；QTM 使用 strong-first 查询顺序和 eager 加载、8 个加载线程。两种引擎顺序运行，每状态各一次，没有清空 OS 文件缓存。

| 相同状态 | HTM 最短成本 | QTM 最短成本 | HTM 证明耗时 | QTM 证明耗时 | QTM / HTM |
| --- | ---: | ---: | ---: | ---: | ---: |
| initial-1 | 18 | 22 | 13.251 秒 | 13.461 秒 | 1.016 |
| initial-12 | 17 | 20 | 1.651 秒 | 0.186 秒 | 0.113 |

生成量与吞吐分解：

| 状态 / 引擎 | 实际生成候选数 | 每秒生成数 |
| --- | ---: | ---: |
| initial-1 / HTM | 1,951,990,044 | 147,308,630 |
| initial-1 / QTM | 1,104,817,692 | 82,074,223 |
| initial-12 / HTM | 188,783,217 | 114,311,952 |
| initial-12 / QTM | 15,625,344 | 83,916,091 |

因此 `initial-1` 的时间倍率约为 `0.566 × 1.795 = 1.016`，`initial-12` 约为 `0.08277 × 1.362 = 0.11275`。QTM 每次生成更贵，但剪枝可能大幅减少总生成量；“QTM 步数更多所以必定更慢”并不成立。

这里的吞吐是单次实测平均，用于分解这些请求，不能保证其他状态仍有相同吞吐。所有 4 个结果都为 `optimal=true`，独立重放通过，所有已搜索层都完整结束，没有通过“找到更短解提前停止”改变排除树。

本次独立原生进程的 eager ready 时间为 HTM 0.674 秒、QTM 4.728 秒，另计于上述证明时间之外。没有主动清空系统文件缓存，且 ready 不保证所有后续访问页都已驻留；它不是冷磁盘启动结论，也不是网页默认 staged 启动时间。

## 3. 从头求解的额外成本

已有最优候选会省去发现该解所需的搜索，尤其可能省去最优成本那一层的大量工作。下面使用项目中 **1.8.0 同一验收阶段、相同状态、15 线程、eager 强资产** 的历史完整求解记录；不与本次预先给定最佳候选的证明时间混算。

| 相同状态 | HTM 原生完整搜索 | QTM 原生完整搜索 | QTM / HTM |
| --- | ---: | ---: | ---: |
| initial-1 | 21.419 秒 | 19.315 秒 | 0.902 |
| initial-12 | 4.594 秒 | 9.917 秒 | 2.159 |

这两个原生计时不含 eager 进程初始化。完整请求墙钟分别为 HTM 22.258 / 4.844 秒，QTM 28.782 / 19.020 秒；搜索与请求计时不可互换。证据来自 `htm-h1-real-release.json` 与 `qtm-q1-real-release.json`，均只有各状态一次验收记录，不是交错重复的统计性能测试。

最新版 **1.10.0 默认启动页面** 已有 QTM 完整请求记录为 17.234 / 7.328 秒，原生搜索计时为 16.316 / 6.432 秒，第一候选生成约 0.937 / 0.891 秒。它们包含 staged 等待和默认调度；该原生计时也不能当作纯证明 CPU 工作时间。此次没有补跑与它们严格配对的新版 HTM 页面测试，因此不把这些数字与旧 HTM 组成新的加速倍率。

对这些样本，可将“已有最佳候选”的证明成本估为上述约 13 秒 / 0.2–1.7 秒；从头求解应额外考虑发现最佳解和初始化的成本。新打乱只有在知道其最短距离、启发式分布或完成有界层校准后，才能给出可靠秒数。没有足够证据给任意打乱承诺一个统一 HTM / QTM 倍率。
