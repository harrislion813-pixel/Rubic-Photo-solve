# QTM 求解器文档审查与下一步优化建议

日期：2026-09-30。审查源码：`c01d90d`（v1.7.1）。本次读取设计、实施报告、正式汇总及部分归档消融数据，并核对当前代码；没有重编译或新增性能测试。下文明确区分历史实测、代码事实与待验证建议。

更新说明：HTM 恢复与 QTM 隔离已在独立实施分支完成，版本为 1.8.0。本文保留为 1.7.1 的历史审查；当前结构、报告复核和下一轮优先级见 [隔离后的项目复审](qtm-isolation-review-2026-09-30.md)。下文“本次没有执行”描述的是此前审查当时的状态。

## 1. 结论

建议下一轮先处理实际配置、强资产接入时机和方向误选，再缩短完整 strong 配置的节点处理路径。需要进一步缩小搜索树时，先改进已有 dual 的成本，再试验能够补充当前强表的新投影。

已完成的仿射坐标、QTM 三轴加强、精确 nibble 和候选通知应保留。现在重做这些工作收益有限；直接扩大 Tail 或默认开启更多六棱块表，也缺少现有数据支持。

最新 [HTM 恢复与 QTM 隔离方案](ai-htm-rollback-qtm-isolation-plan.md)适合作为集成边界：QTM 算法迭代放在独立引擎中，HTM 恢复可以单独交付。本次没有执行该方案。

## 2. 文档中的实测结果应如何理解

主要依据是 [第二轮实施报告](qtm-next-optimization-report.md)及其 [正式汇总](benchmarks/qtm-round2-summary-2026-09-29.json)。旧行动方案描述历史任务与目标，不应把未勾选清单理解成当前实现仍缺失。

| 项目 | 第二轮结果 | 对下一步的含义 |
| --- | --- | --- |
| 公开集严格证明 | 80/144 → 120/144 | 强配置确有收益，但这些状态已经用于诊断 |
| 冻结未见集严格证明 | 72/96；6 个状态三次均超时 | 仍存在稳定难例；该集合已经公开，后续调参后不能继续宣称未见 |
| 公开集 PAR-2 | 62.827 → 32.061 秒 | 是含超时惩罚的综合指标，不是所有请求的实际平均加速比 |
| 完整排除 20/21 成本的两例 | 生成数改善约 1.51 倍，墙钟约 3.65 倍 | 每个节点处理变快占了较大收益，进一步减少搜索树仍有空间 |
| 初始化与工作集 | 完整 eager 约 8.507 秒；峰值约 3.45 GiB | staged 的基础 ready 约 0.84 秒不能代表完整强资产可用 |
| 热服务候选 | 3 秒预算下候选代价中位数 24 | 是可行上界；不能替代严格排除 20/21 成本的工作 |

两轮报告严格证明的正式口径是 4 线程、60 秒、每状态 3 次，关闭原生候选和证明缓存。HTTP 候选结果使用不同线程配置，不能拼接为同一算法加速指标。启动结果没有人为清空 Windows 文件缓存，真正冷文件缓存启动仍未知。

需要修正文档使用方式的三点：

- 本地验收强配置不代表默认 CI 发布包。当前 `release/build_windows.ps1` 的 `QtmProfile` 默认是 `None`，仓库根 CI 调用也没有显式选择 QTM 配置。必须核对实际包，而不是只看源代码版本。
- 旧强优化报告中 Phase-1 SHA-256 被截短；完整值应以资产 manifest 为准。历史 EXE、当前源码与最终 EXE 是不同来源，比较时继续记录实际 hash。
- 报告中的方向描述偏窄：当前代码在逆态根下界更大时直接选逆向；其余情况只要满足预算条件也可能探测，并不限于两者下界相等。

## 3. 第一优先级：让当前请求及时用上已验证强表

`native/src/main.cpp` 已分别发布 strong 与 Tail 的不可变快照，没有必要等 Tail 完成才发布 strong。但 `native/src/solver.cpp` 只在成本层边界调用 `asset_snapshot_callback`。

因此存在以下待测场景：首次请求以基础表开始，进入较长的 20/21 成本层；强表后台验证已结束，搜索仍要等这一层结束才升级，甚至直到 deadline 都使用基础表。现有报告证明短请求能逐步升级资产，没有测出困难首次请求的这段等待。

建议补充 `strong_ready_time`、`strong_adopted_time`、当前层已用时间和剩余 deadline。先确认是否存在明显接入延迟，再实现受控的提前升级：

1. 在低频控制检查点发现新 strong 快照，判断是否值得重启当前层。
2. 停止并等待旧 worker 退出，保留此前已完成的排除成本。
3. 从根用新快照重建坐标，重新计算正逆态根下界及方向策略，继续同一成本层。
4. 被中断的层不进入证明缓存；升级不延长原始 deadline。

这项机制与用户取消、超时、候选缩短预算应有不同原因标记。重启会丢弃当前层工作，不能无条件频繁触发；优先针对 base→strong 的首次升级验证。Tail 到达可以继续采用层边界策略。

这项工作的主要指标是困难首次请求的强表采用延迟、最终完成成本及端到端耗时。已经预热的纯证明测试不能验证它的收益。

## 4. 第二优先级：改进方向选择，减少个案退化

历史数据中的 `legal-20271018`，证明耗时中位数从 2.832 秒变为 6.595 秒；新版三次均选逆向。这个现象支持调查方向策略，但不能仅用找到解后提前停止的总生成数，证明逆向完整搜索树一定更大。

当前策略有两个值得改进的因素：

- 根逆态下界较大时直接选择逆向，没有再比较两边工作量。较强根下界可以安全提高全局证明下限，但它不是搜索成本预测器。
- 截断的 DFS 采样用拒绝率选择方向。前 50,000 个生成候选可能集中在少数前缀，较浅采样的拒绝率也未必能预测深层搜索。

建议始终保留 `max(h(s), h(s⁻¹))` 作为合法根下界，方向单独决策。先在两种方向上比较相同完整排除成本，再试验覆盖多个根前缀的分层采样，记录采样是否完整、拒绝率、生成数、时间和深度分布。样本不足或差异很小时采用稳定默认值，不由少量噪声触发切换。

方向可以在完整成本层结束后重新选择，已完成的排除事实仍针对同一原始状态有效。禁止在未完成子树中直接切换；需要提前切换时从根重启该层。staged 强表升级后应重新评估方向，避免继续沿用基础表得到的判断。

验收要同时报告总体收益和逐状态退化，采样开销计入 deadline。不能针对 `legal-20271018` 写状态特例。

## 5. 第三优先级：专门优化完整 strong 搜索路径

### 5.1 删除不再参与查询的坐标更新

当前完整 strong、`strong-first` 配置已经跳过被支配的 Phase-1 查询，但 `CoordinateTables::evaluate` 仍更新主轴 `slice`，`ensure_axis` 仍更新另外两轴的 `axis_slice`。`materialize` 不使用这些字段。

当小 Phase-1 预筛也关闭时，这些转移可以省略。建议在资产快照建立时确定“哪些坐标必须维护”，将完整 strong 路径与 base/部分表路径分开选择，同时减少没有启用的 Edge 字段与每候选策略判断。

必须保证缺表、部分表、小表预筛开启时仍维护所需字段；被接受的节点不能携带未初始化但后续会使用的坐标。对相同完整排除成本验证生成数和下界一致，收益应体现为更低的每生成候选耗时。

### 5.2 重新核实预取消融

这是本次发现的证据缺口：当前 `alternative_order` 分支的 `query_strong` 直接调用 `distance`，没有读取 `prefetch_strong`；预取逻辑只在 legacy 查询路径中执行。

归档文件 `ablation-prefetchoff-cost18.json` 和 `ablation-prefetchon-cost18.json` 均指定 `--pdb-query-order=strong-first`。因此当前实现不能用这类开关对照证明预取无收益。归档构建的源码字节 hash 与当前提交不同，本次没有还原它的完整构建源，历史运行是否具有相同问题仍需核实。

先增加实际预取执行次数，确认实验开关确实改变了执行路径。随后才比较有效预取、少量兄弟索引批量准备、不同轴的查询顺序。默认仍可关闭预取；这次审查没有证明预取应该开启。

### 5.3 用成本与条件拒绝率选择查询顺序

当前顺序先查三个 strong 轴，再查 Corner。建议统计不同剩余成本、slack 和轴位置下的查询成本与拒绝率，试验先查询父节点中较强的轴，以及在适合的层先用 Corner 拒绝。

统计必须是经过前序筛选后的条件拒绝率。只看总命中率不能决定最佳顺序。重新排序还要保留三轴相等加强的合法性，不能漏掉接受节点需要的投影。

完成 profiling 前不能断言当前瓶颈完全来自内存带宽。线程扩展性已有良好数据，暂不把工作窃取重写放在上述热路径之前。

## 6. 第四优先级：缩短完整强表验证时间

当前 nibble loader 已按块并行校验，但块内逐字节做 FNV 累积、两个 nibble 范围检查和最大值更新。完整 strong 验证约 7 秒，不能把它全部归因于文件读取。

建议先分别测量只读扫描、checksum、范围/最大值验证和对称辅助表初始化，再选择实现：向量化 nibble 检查、减少逐字节分支、合适的校验线程额度。若 checksum 本身占主要成本，再版本化引入更快的块校验算法，保留旧格式读取。

所有强剪枝仍须使用已完整验证的数据。不能用关闭校验、只检查 mtime/size 或仅缩短基础 ready 来宣称完整初始化达标。后台校验线程也应计入资源额度，评估它与候选、证明争用 CPU 的影响。

## 7. 真正缩小搜索树：先降低 dual 成本，再试补充投影

选择性 dual 已使固定层生成数减少约四分之一，却让墙钟变慢约 6%；原型有剪枝价值，当前实现成本未抵消收益。BPMX 的额外拒绝很少，不宜直接默认开启。

当前 `dual_bound` 从紧凑状态重建逆态，依次查询 Phase-1、Corner、单轴 strong；它没有 cutoff，也没有因已超过预算而提前结束。建议先做以下改动：

- 完整 strong 配置省去同轴被支配的 Phase-1 查询。
- 将 remaining/cutoff 传入逆态查询，某个合法下界足以拒绝后立即返回。
- 比较只在任务根、特定 slack/剩余成本、特定前序筛选结果下触发的策略。
- 只有逆态提取仍占主要成本时，再研究增量或专用逆态坐标。逆态动作是左乘，不能直接复用正态右乘转移。

只有完整层墙钟改善才启用。减少生成数与减少时间要分别报告；不重复把现有栈上重建宣称为新的“去堆分配”优化。

如果这些步骤之后，困难请求仍主要卡在完整 20/21 成本层，建议试验补充当前 strong 投影的七棱块 PDB。当前三轴 strong 约束朝向与切片棱位置/次序，Corner 约束角块；新投影应优先补充剩余棱排列约束，而不是简单重复相近下界。

不计对称归约的七棱块位置加朝向有 `12P7 × 2^7 = 510,935,040` 项，byte 距离主体约 0.476 GiB。格式压缩须先确认完整最大距离，不能假定仍能用当前 nibble 格式。先做资源估算与原型，在经过当前 strong/Corner 后的存活节点上测额外拒绝量和真实查询成本；没有整体收益就停止扩大。

重叠 PDB 先取最大值；直接相加没有可采纳性保证。需要加法组合时必须另行设计动作成本分摊并证明。

候选优化继续保留，但有一条边界：候选成本从 25 降到 24，不会自动缩短仍须完整排除的 20/21 成本层。下一步应记录候选上界与已证下界的差值及证明线程投入，用整体证明时间决定候选时间份额。

## 8. 精简验证与执行顺序

沿用最新隔离方案的 2 个固定诊断状态与 2 组实拍，先检查实际包、资产、引擎、候选交付和 deadline；不默认重跑 48+32 长验收。已有基线在配置与来源不变时复用。

建议执行顺序：实际配置与隔离基线 → staged 强表接入 → 方向选择 → strong 专用热路径/有效预取对照 → 完整校验 → 低成本 dual → 新 PDB 原型。

| 改动 | 开发期主要验证 |
| --- | --- |
| 路由、隔离、资产接入 | 实际包请求、采用时间、取消/升级状态、完成层缓存 |
| 坐标字段省略、查询顺序、预取 | 相同完整成本、关闭候选与方向，比较生成数、查询结果、墙钟 |
| 方向策略 | 相同总线程和 deadline，区分完整层与截断/找到解的层 |
| 新剪枝、dual 或新 PDB | 对应规则的独立 oracle/证书，再做完整层对照 |
| 候选资源策略 | 冻结资产阶段，记录候选上界、已证下界、证明投入及终态 |

方向问题调查可临时加入已有 `legal-20271018`，明确这是定点故障诊断；不将新增诊断扩成默认全量任务。两组实拍只支持个案结论，不能据此报告总体成功率或 p95。若后续要作广泛性能声明，再单独冻结不参与调参的验收集。

暂缓 Tail-9/10、全层 TT、默认更多六棱块表和工作窃取重写。已有消融未提供稳定收益；先让实际请求使用已交付的能力，并测清每个额外剪枝的成本。

## 9. 算法资料与适用边界

Kociemba 的 [剪枝表说明](https://www.kociemba.org/math/pruning.htm)解释了联合投影、对称索引和模 3 距离跟踪。其模 3 跟踪依赖单步距离变化属于 −1/0/+1；本项目 QTM 半转代价为 2，不能直接照搬这个前提。这也是继续采用精确 nibble、暂缓模 3 改造的理由。

[QTM 上界证明作者的网站](https://www.cube20.org/qtm/)给出最大最短距离 26，并说明其全局证明使用集合求解且没有为每个状态计算最短解。这一数学上界不提供本项目任意状态的单机证明时间保证。

本次建议的收益都需要项目自己的对照实验确认，不引用其他求解器的加速倍数作为本项目预期结果。
