# QTM 正式应用前的项目审查与提速方案

日期：2026-10-01（Asia/Shanghai）。审查基线：`main` / `931662805df003aeaeadad419fe10296961c94d2`，应用版本 `1.9.0`。

**建议下一轮先实现“基础表快速交付候选，强表就绪后及时接管证明”，再优化强表搜索吞吐。** 现有实现已经具备独立 QTM 引擎、完整强表、正确性检查及安全热复用；当前主要缺口是这些能力没有在默认困难请求中有效配合，以及 QTM 尚未拥有正式发布所需的持续验证。

## 4. “正式应用”的目标与范围

正式应用意味着：安装后使用统一入口，快速获得有效 QTM 候选；验证在可控预算内持续推进；只有可靠证明完成才显示严格最短；QTM 的故障、内存和长请求受控；交付包具有独立验证。保持 HTM 默认稳定入口，QTM 作为可正式选择的独立功能。

二阶可按准确全表单独验收。三阶不能通过去掉“实验”文案或把候选当作最短来满足提速目标。

以下是**建议的参考机验收目标，均不是当前已有保证**：

| 目标 | 建议门槛 |
| --- | --- |
| 保住首解体验 | `initial-1/12` 新进程后台首候选 ≤2 秒；TTL 内不同浅状态的热请求 ≤0.3 秒；页面时间另测 |
| 强表确实参与 | 在期限仍足够、已通过接纳的请求中，strong ready 后 ≤0.5 秒开始用于证明；同时记录旧任务最终退出时间 |
| 减少初始化 | 完整 strong ready 争取从约 9 秒降至 ≤5 秒；先确认可达到的分项收益，不牺牲完整验证 |
| 真实严格证明 | 最终包中 initial-1/12 各一次 30 秒请求都完成成本分别为 22/20 的严格证明，并重放动作 |
| 热搜索 | 同场固定完整层不得持续退化超过 5%；简单优化需稳定 ≥5% 收益，复杂剪枝/调度需约 ≥10% 收益才引入默认 |
| 资源隔离 | HTM 附加让出等待目标 ≤1 秒；故障/取消/内存拒绝后没有残留 loader、请求或错误证书 |
| 正确性 | 坐标/剪枝 oracle、取消与升级覆盖账本、损坏资产回退、最终解重放全部通过 |

两个实拍样本证明成本的依据是项目已有严格运行记录，本次只重新检查了 initial-12。它们是验收用例，不代表所有真实魔方。

任意状态在 30 秒内完成严格最短不能作为无条件承诺。QTM 的最大最短距离为 26 是数学距离上界，不给出本项目的单机证明时间上界；证明作者也区分集合覆盖与逐状态最短求解。[原始说明](https://www.cube20.org/qtm/)

## 5. 第一交付阶段：重排加载与证明，保留快速候选

### A1. 完整 QTM 的最小启动资产

涉及 `qtm/native.py`、原生 `main.cpp` 与构建/资产验证。

1. 将完整 QTM 基础能力与 fallback 初始化分开；完整 QTM Corner、Phase-1、候选表就绪后先交付 base ready。
2. 完整 QTM 路径不主动映射那三项未被使用的 HTM 辅助表。若 QTM 表缺失、校验失败且允许回退，再有预算地加载私有 HTM 辅助资产，清楚记录实际 profile。
3. 继续使用现有 strong、Tail 文件，不重建大型资产。第一版保持包内回退文件，收益来自运行时加载策略。
4. 记录基础坐标、QTM 主表校验、候选表、各辅助资产的分项时间与映射字节；同状态对照必须核对候选、合法下界、完整层结果等价。

### A2. 首选原型：候选先行，强表优先，限制 base 深搜

相比继续进入数十秒的 base 成本层，先试验一个改动较小、可单独交付的策略：

- base ready 后立即运行已有候选器；允许一个有上限的浅层严格搜索窗口，例如累计约 0.3 秒，数值作为实验参数。
- 强表接纳成功、仍在验证时，不再无条件派发长 base 证明。候选保留 1 个额度；loader 获得总额度允许的至多 8 个校验线程，其余额度按策略使用或暂时空闲。
- strong 完整验证并发布后，立即从最后完整排除成本继续严格搜索，保留原 deadline 和最佳已验证候选。未完成的浅层窗口不能进入证明缓存。
- 不等待 Tail 才开始 strong 搜索。Tail 就绪后的接入单独统计。
- warm strong 直接开始证明；缺强表、内存拒绝或小线程配置使用明确的 base/串行策略，不能一直等一个不会到达的阶段。

该策略需要把候选生命周期与 proof 层调度适当分开；当前候选创建在 `NativeOptimalSolver::solve` 内，不能反复调用完整 `solve()` 并重复生成候选/重置预算来拼接流程。

先做“相同 loader 配额，只改变 base 深搜策略”的对照，再单独比较 4/8 校验线程。当前 eager 实现没有把 managed loader 参数传入同步 strong 构造，实际校验并发与 staged 不同；这是本次整套加载方式比较的混杂因素，不能冒充线程数消融。

A2 的主要判定是：候选仍快，strong 提前参与，严格证明更快。单独提高 strong ready 或 adoption 指标而没有改善请求结果，不算完成本阶段。

### A3. 完整校验的分项提速

先分别计时读入/缺页、checksum、nibble 范围与最大值、对称辅助表初始化。保留完整校验后再选择改动：

- 保持 v4 格式，试验查表或向量化的 nibble 合法性/最大值检查，比较与 checksum 合并扫描和分开扫描的总墙钟。
- 不把有串行依赖的 FNV 循环简单标成可 SIMD 化；不能改变现有 chunk checksum 的含义。
- 只有 checksum 确为主要成本，才考虑新格式的快速分块散列。保留旧格式读入、完整数据验证、截断/错 metric/错误覆盖标记/损坏块测试；资产转码与建表分开。
- 对称辅助表只有在分项收益足够时才做版本化缓存，仍需校验来源与内容。

不以 mtime、size、manifest 存在或跳过数据校验代替可供严格剪枝使用的已验证资产。

## 6. 第二阶段：需要持续 base 证明时，保留已完成子树

如果 A2 的限制 base 策略在短任务上损失过大，或困难请求仍需要充分利用加载窗口，再实现**按子任务采用快照**。它是条件性工作，不先做整套搜索器重写。

现有队列已经把根搜索拆成带 `path / state / depth_left / last_face` 的 `SearchTask`（`solver.cpp:296`、`:748`）。可在此边界扩展：

1. 每个任务绑定不可变资产快照和坐标需求；已完整排除的前缀子树保留其完成记录。
2. 新任务取出时采用最新已校验快照。base 状态没有维护 strong sorted-slice，必须先由完整状态重建新坐标、重算下界，不能只替换 PDB 指针。
3. 进行中的任务在低频检查点响应升级。第一版可只重跑该任务根，保留其他已完成任务；进阶版本才保存任务内部未搜索前沿。
4. 为长任务设置受控检查与拆分。当前最长 base 子任务约 13.8 秒，仅在下次出队升级不足以保证及时采用；每任务每次 strong 升级最多重排一次，记录实际重复工作。
5. 将 `Exhausted / Found / UpgradeYield / Cancelled / Deadline` 明确区分。原来只返回 `false` 的路径不能直接等价为“已完整排除”。
6. 拆分父任务与登记子任务须保持覆盖账本原子性；只有该成本的全部任务完全覆盖，才能更新 `completed_depth`。升级、取消和超时不签发未完成层证明。
7. 同一成本层内保持方向与动作规范化规则不变；不能把正向已完成前缀套到逆向队列。TT 仅复用完整搜索得到的合法记录，并绑定相应规则；首版升级可直接清空 TT。
8. Tail 优先在任务边界采用。不要为了晚到的 Tail 再把已完成的 strong 子树全部重跑。

正确性依据是：在同一成本预算与同一完整前缀划分下，旧合法下界已完全排除的子树仍然无解；新合法下界可继续排除剩余子树。该理由不允许把“访问过节点”当作“完成了子树”。

验证应主动在分裂、入队、DFS 中段、发现解和截止前插入升级/取消事件，与独立浅层 QTM oracle 比较。还要检查零漏任务、重复计数不会提前结束，以及不同快照状态的坐标重建。

验收同时记录 ready→首次使用、旧快照最后使用、完成任务覆盖、重跑生成量、额外队列内存与最终墙钟。不能只报第一次 adopted 事件。

## 7. 第三阶段：让完整 strong 搜索本身更快

### B1. 先修方向决策与测量

继续使用 `max(h(s), h(s⁻¹))` 作为合法根下界；独立决定搜索方向。当前一次对照中 base 选逆向、strong 选正向，说明测量必须固定方向才能区分表强度和方向影响。

先在现有两个诊断状态的相同完整成本上比较正向/逆向；需要困难方向样本时至多再加两个预先冻结的旧诊断状态。方向策略只在完整层边界重评估；子任务迁移期间不改变整层方向。

新策略可按上一完整层工作量决定是否探测，并对多个固定根前缀均衡采样。采样计入总期限。不要继续仅用根下界更大或一段截断 DFS 的拒绝率决定深层方向；也不因两个短用例就全局关闭探测。

### B2. 完整 strong 路径专门化与低开销统计

先采样剖析，再选择一项实现：

- 将完整 strong/base/partial 的策略选择移到层或任务入口，减少每个 child 的动态配置判断。独立 QTM 目录仍保留大量通用 metric 路径，适合试验专门化，但需要真实吞吐数据。
- 分离验收需要的详细计数和生产必要的进度计数，测量每 child 的统计写入成本；不删除证明、deadline、取消或关键诊断。
- 比较各 remaining/slack 区间的条件拒绝率与查询成本，再试 Corner-first、父节点较强轴优先等有限策略。当前 Corner 拒绝率是在 strong 已筛选后的数据，不能用它直接推断 Corner 提前查询的收益。
- 接受节点必须具备后续需要的所有坐标，三轴同值加强仍需正确取得相应轴值。

上一轮 slice omit 约 -0.42%/-0.01%、有效预取约 +0.30%/-0.02% 的结果不足以启用。当前 prefetch 紧接 load，缺乏独立工作来隐藏延迟；只有明确设计出可重叠的兄弟/轴查询流水线并纳入额外查询成本，才值得重新试验。

### B3. 低成本 selective dual

现有 `dual_bound`（`solver.cpp:510`）重建逆态后依次查询 Phase-1、Corner、strong，没有 cutoff。可按顺序做独立实验：

1. 传入 remaining，任一合法逆态下界足以拒绝就返回。
2. 完整 strong 下省去被支配的同轴 Phase-1，分别比较 inverse strong-first 和 Corner-first。
3. 限制在任务根或经过前向筛选后、slack 0/1 的区间触发，再由实际成本调节。

仅减少生成量不够；必须计算逆态提取与查询成本后的完整层墙钟。`dual=root` 与 `off` 当前都不执行节点 dual，不再做空消融。逆态动作涉及左乘，不能直接套用正向增量转移。

### B4. Portable PGO

算法默认稳定后再实施：

- 修正 `-Portable` 的传递，PGO 前后保持同一通用 x64 编译模式。
- 使用独立训练状态，覆盖候选、base、strong 与取消/控制路径；与性能验收输入分离。
- 写入真实训练输入/命令、编译器、源码、资产与二进制散列，检查缺失/不匹配 profile；现有脚本仅记录整份 `native_cases.json` 散列不足以完整描述训练。
- 比较 Portable O3 与 Portable PGO；通过实际包与目标 x64 机器验证后再选默认。

GCC 的 profile-use 会启用基于实际运行信息的优化，它不自动保证更快，也不自动赋予 CPU 可移植性。[GCC 官方选项说明](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html)

## 8. 第四阶段：搜索树仍过大时，研究互补 PDB

进入条件：请求已经及时采用 strong；加载、方向和单位生成成本已测清；关键成本层仍因树规模达不到目标。届时比较以下候选，而不是直接扩 Tail：

| 投影 | 未归约项数 | byte 距离主体 | 需验证的问题 |
| --- | ---: | ---: | --- |
| 全 12 棱排列，不含朝向 | `12! = 479,001,600` | 约 0.446 GiB | 能补跨切片排列关系；rank/unrank 与转移提取可能昂贵 |
| 七棱位置与朝向 | `12P7 × 2^7 = 510,935,040` | 约 0.476 GiB | 含更多联合朝向信息，但与现有投影重叠；选择哪些棱需冻结 |

这是候选设计及状态数估算，没有本项目速度实证，不预设哪一个更好。不能只因表项数较少就选它。先用索引微基准、已证浅层状态及较小投影原型筛选可行性，再决定生成哪一张完整表；完整表生成后测量 strong/Corner 之后的额外拒绝与总墙钟。小投影或部分表不能提前证明深层收益。

要求：

- QTM 可用 12 种单位代价四分之一转 BFS，或正确处理 18 种权重 1/2 的最短路；不能把半转当作单位边。
- 首版存准确 byte，确认最大距离后再选压缩；不能假定仍可放进保留特殊值的 nibble。
- 建表峰值需计 frontier、访问位图、临时数据和校验。全 12 棱排列的 `12! × 18 × uint32` 转移表单独约 32.1 GiB，不适合直接随距离表驻留；设计按需或分解转移。
- 重叠投影取最大值；加法组合必须另有动作成本分摊证明。部分覆盖的未知项只能使用有证明的保守下界。
- 新增表的默认启用门槛建议更高：困难完整层墙钟至少约 20% 改善，内存、初始化和包体符合目标机器，再纳入正式配置。

现有 sorted-slice 联合表和三轴方法有明确的原始设计依据，但新投影的收益与可采纳性仍需本项目验证。[Kociemba 最优求解说明](https://kociemba.org/math/optimal.htm)、[剪枝表与对称说明](https://kociemba.org/math/pruning.htm)

继续暂缓 Tail-9/10、全层 TT、无依据的工作窃取重写和模 3 距离改造。模 3 原说明使用单位动作下距离变化至多 1 的前提；本项目半转代价为 2，不能直接照搬其跟踪规则。

## 9. 正式发布的工程门槛

提速与稳定性一起完成，不能用一组更快的脚本代替正式包资格。

1. **QTM 独立 CI。** 增加 QTM Portable 编译、原生协议/动作成本、浅层独立 oracle、partial/base/strong 读取与切换验证。普通提交使用有界夹具；完整大表通过版本化缓存或专门发布验收提供，不在每个提交重新建表。缺必需资产应明确阻断相应门禁，不能静默 skip 后视为 QTM 通过。
2. **能力声明。** 区分二阶准确表、三阶 base/strong、资产未就绪/就绪/实际采用。二阶不因三阶 EXE 未安装而被误判不可用。损坏或拒绝加载强表时说明实际配置，不能沿用 strong 标签。
3. **有界请求管理。** 给 QTM jobs 加上容量和终态回收，限制诊断快照大小；等价活动请求考虑去重，明确不同 timeout 的处理，不能借重试延长原 deadline。先用轻量并发/终态模拟验证。
4. **用户可理解的进度。** 展示候选成本、已证下界、差值及正在初始化/证明。用真实的已完成层更新下界，未完成层不能给出虚假的百分比。候选、超时和严格最短继续分别显示。
5. **生命周期。** 保留现有 bounded reuse，并对新 loader/快照边界复测 HTM 抢占、真实 TTL、内存拒绝、进程故障、旧代际、取消与无限期限。总额度在 1/2/3 线程时也必须成立。
6. **交付包。** 对最终源码构建一次候选 QtmStrong，在独立 Unicode 目录验证 EXE/资产/源码身份与真实页面；使用统一的正式入口验证，不能只让另一个专用启动脚本达到性能目标。

只有下面的正确性、性能与资源门槛共同通过，才建议将对应 QTM 能力改为正式状态。二阶与三阶可以分别放行。

## 10. 执行顺序、预算与决策规则

| 阶段 | 首要产物 | 通过后再做什么 |
| --- | --- | --- |
| 0：基线与构建 | 修复开发环境版本元数据；冻结当前可复现来源；建立 QTM 原生门禁 | 开始策略改动 |
| 1：加载与首请求 | A1 最小资产 + A2 候选先行/strong 优先；A3 依据分项剖析推进 | 先验证快速候选与严格完成能同时改善 |
| 2：子任务升级 | 仅在必要时实现快照任务化、完成覆盖账本与有界重跑 | 正确性通过后再测收益 |
| 3：热搜索 | B1 方向、B2 专门化/统计、B3 selective dual，每次一个变体；默认稳定后做 B4 PGO | 只合入有稳定墙钟收益的变体 |
| 4：互补 PDB | 有条件的资源估算、建表与查询原型 | 收益与内存门槛通过才进入包 |
| 5：发布资格 | 有界任务管理、能力/UI、目标硬件与最终包验收 | 满足门槛才调整正式状态 |

开发期沿用最多两个主诊断状态，每配置每状态 3 次、每次 ≤5 秒；初始基线和一个变体合计最多 60 秒搜索。新算法确需困难状态时最多增加两个并提前冻结。冷请求先用 initial-12，每配置一次 ≤30 秒；最终在候选包检查 initial-1/12。保留超时，不为寻找好结果追加 180 秒或恢复旧 48+32 大集合。

为“正式应用”而新增的较广资格验证放在**最终候选包**，不用于日常调参：建议另冻结 12 个未用于调参/PGO 的合法状态，逐个保留候选、严格结果、完成成本和超时。每状态每配置一次、30 秒上限；新旧配对最坏 12 分钟请求预算。按同机同资产对照，建议要求严格完成数不下降、含超时惩罚的 PAR-2 降低至少 20%，并逐项调查新增超时；只支持该固定资格集结论，不宣称总体成功率或 p95。PAR-2 的超时项记为两倍期限，不能删除失败样本。

较广资格集是正式宣传性能前的最后一道验证建议，本次没有运行。若只完成两个诊断与两个实拍，应明确限定结论范围，不能据此宣布普遍性能达标。

测量纪律：

- 热搜索使用相同资产、方向、成本界、候选上界与缓存设置；纯吞吐只比较完整排除层。
- 端到端使用真实候选和原始绝对 deadline，分别报告新进程、热 resident、OS 文件缓存状态。
- A/B 使用交错顺序；搜索期间不并行构建、跑测试或另一个性能实验。
- 保留 baseline/current EXE hash、源文件/资产 hash、实际参数、原始事件及失败尝试；不同二进制或不同配置不能拼成一个提速比例。
- 新剪枝先通过 oracle；新任务迁移先通过覆盖/中断正确性。线程数和策略不要同时变动后归因给其中一项。
- 优化没有过门槛就维持现有默认并记录停止原因。新 PDB、扩大 Tail 与更多并发不作为掩盖无收益实验的后续步骤。

下一轮最先可实施的工作包是：**环境与 QTM CI → 完整 QTM 最小启动资产 → 候选先行、strong 优先的有界证明调度 → 一次实际包验证**。该工作包通过后，才决定是否值得承担子任务迁移与新 PDB 的复杂度。
